# Таблица семейных финансов — проектное решение

Дата: 2026-09-18

## Задача

Заменить файл «План финансов» в Excel веб-приложением, которое работает одинаково
на компьютере и на телефоне и никогда не показывает устаревшие данные.

Сейчас файл лежит в облаке и редактируется с двух телефонов. Каждое устройство
работает со своей копией, копии расходятся, и правка, сделанная одним человеком,
может не дойти до второго. Это и есть главная боль, ради которой затевается проект.

Второе назначение — показать уровень владения разработкой: микросервисы, очередь
сообщений, документная база, живая синхронизация, тесты, контейнеры, автоматическая
сборка и развёртывание.

Третье — разобраться с MongoDB на практике, а не по верхам.

## Что именно строим

Аналог Excel, а не учётную программу. Приложение не знает слов «приход» и «расход» —
оно знает листы, ячейки и формулы. Смысл колонок задаёт пользователь, вписывая
заголовки в ячейки, ровно как сейчас в Excel.

Из возможностей Excel в первой версии:

- **Формулы**: арифметика (`+ - * / ^`), скобки, ссылки на ячейки (`B3`),
  абсолютные ссылки (`$F$2`), диапазоны (`B3:B90`), функция суммирования.
- **Листы-вкладки** — один лист на месяц (`08.26`, `09.26`, `10.26`), с созданием
  нового месяца копией предыдущего: структура и формулы переносятся, значения пустые.
- **Оформление ячеек**: заливка, жирный шрифт, число знаков после запятой,
  выравнивание, ширина колонок.

Сознательно не делаем: импорт и экспорт xlsx, работу без интернета, диаграммы
внутри листа, объединение ячеек, условное форматирование, функции сложнее суммы.

## Пользователи

Двое — владелец и супруга. Обоим доступна одна книга целиком, без разграничения прав
внутри неё. Модель данных при этом рассчитана на несколько книг и несколько
участников: это не усложняет код, но снимает потолок на будущее.

## Архитектура

### Разделение на сервисы

**`sheet-service`** отвечает за настоящее время: пользователи и вход, книги, листы,
ячейки, оформление, вычисление формул, рассылка изменений по WebSocket. Единственный
сервис, с которым разговаривает редактор таблицы.

**`history-service`** отвечает за прошлое: неизменяемый журнал всех правок, состояние
листа на любой прошлый момент, восстановление, месячные сводки.

Связь односторонняя: `sheet-service` публикует события в RabbitMQ, `history-service`
их читает. Обратного потока через очередь нет. Если сервис истории лежит, таблица
работает как ни в чём не бывало, а журнал догоняет из очереди после подъёма.

Единственное синхронное обращение в обратную сторону — восстановление состояния:
`sheet-service` по HTTP запрашивает у `history-service` снимок листа на нужный момент
и применяет его у себя как обычную пачку правок. Запись по-прежнему принадлежит
только `sheet-service`.

### Почему граница проведена здесь

Рассматривались два других варианта.

Вынести вычисление формул в отдельный сервис — заманчиво, потому что нагружает
очередь настоящей работой, но кладёт пересчёт на критический путь: значение итога
приходило бы отдельным сообщением с задержкой. Пересчёт нескольких сотен ячеек
занимает микросекунды, гонять его через очередь незачем.

Вынести вход и пользователей в отдельный сервис — классика, но на двух пользователях
такой сервис почти пуст, и это видно невооружённым глазом.

Выбранная граница отделяет быстрый путь записи от медленного пути анализа. Это
разделение из реальных систем, и очередь в нём используется по назначению.

### Контейнеры

| Контейнер | Роль |
|---|---|
| `traefik` | вход, HTTPS, автопродление сертификата |
| `web` | nginx со статикой фронтенда |
| `sheet-app` | Laravel 13, API таблиц |
| `sheet-ws` | тот же образ в режиме WebSocket-сервера (Laravel Reverb) |
| `history-app` | Laravel 13, API истории и сводок |
| `history-worker` | тот же образ, потребитель очереди |
| `mongo` | MongoDB |
| `rabbitmq` | RabbitMQ с панелью управления |
| `mailpit` | перехват почты в разработке |

Локально всё поднимается на портах 8080 и 8443 — порт 80 на машине разработчика
занят другим проектом.

## Как устроена синхронизация

Единственный источник правды — база. Копии на устройствах нет.

У каждого листа есть номер версии, растущий с каждой применённой правкой. Клиент
всегда знает, какую версию он показывает.

Порядок при правке ячейки:

1. Клиент отправляет пакет правок и номер версии, которую он видел.
2. Сервис сохраняет сырой ввод, пересчитывает зависимые ячейки, увеличивает версию
   листа и отвечает пакетом всех изменившихся ячеек вместе с новой версией.
3. Тот же пакет уходит по WebSocket в остальные открытые вкладки и в RabbitMQ.
4. Клиент, получивший пакет по WebSocket, применяет его, если номер версии идёт
   ровно следом за его текущим. Если между ними разрыв — значит сообщение потерялось,
   и клиент перезагружает лист целиком.

Полная перезагрузка листа происходит также при восстановлении соединения и при
возврате на вкладку после ухода в фон. Телефон, пролежавший в кармане полдня,
на первом же касании подтягивает актуальное состояние.

Конфликты правок разных ячеек не возникают в принципе: каждая ячейка — отдельный
документ в базе. При правке одной и той же ячейки побеждает записавший последним,
и второй немедленно видит результат.

## Модель данных

Две базы в одном экземпляре MongoDB: `finance_sheets` и `finance_history`. Разные
базы, а не разные коллекции — сервисы не должны читать чужие данные напрямую.

### Коллекции `sheet-service`

**`users`** — `email` (уникальный индекс), `name`, `passwordHash`, даты.

**`workbooks`** — `name`, `ownerId`, `memberIds`, даты.

**`sheets`** — `workbookId`, `name` (`10.26`), `position`, `version`, `rowCount`,
`columnCount`, `columnWidths`, даты.

**`cells`** — `sheetId`, `row`, `column`, `input` (сырой ввод, `120` или `=СУММ(B3:B90)`),
`kind` (`number` / `text` / `formula` / `empty`), `value` (вычисленное), `error`,
`format`, `dependsOnCells`, `dependsOnRanges`, `updatedBy`, `updatedAt`.

Индексы: уникальный `{sheetId, row, column}`; многоключевой `{sheetId, dependsOnCells}`
для обратного поиска зависимых; `{sheetId, dependsOnRanges.minRow, dependsOnRanges.maxRow}`
для поиска формул, чей диапазон накрывает изменённую ячейку.

**`refresh_tokens`** — `userId`, `tokenHash`, `expiresAt` с TTL-индексом, `createdAt`.

### Почему ячейки — отдельная коллекция

Напрашивается хранить ячейки массивом внутри документа листа: лист читается одним
запросом, всё рядом. Так делать нельзя по трём причинам.

Первая — конкурентная запись. Правка одной ячейки становится записью всего документа
листа. Два человека, правящих разные ячейки, начинают затирать друг друга.

Вторая — размер документа. В MongoDB он ограничен 16 МБ, и лист на несколько тысяч
ячеек с оформлением к этому потолку подбирается.

Третья — поиск зависимых ячеек. При отдельной коллекции это индексный запрос. При
вложенном массиве пришлось бы вычитывать весь лист и перебирать его в памяти.

Разбор этого и остальных решений по базе — в `docs/mongodb.md`.

### Коллекции `history-service`

**`cell_changes`** — журнал, только добавление: `workbookId`, `sheetId`, `sheetName`,
`row`, `column`, `ref` (`B5`), `before`, `after`, `origin` (правка пользователя или
следствие пересчёта), `sheetVersion`, `userId`, `userName`, `occurredAt`.

**`sheet_snapshots`** — снимок состояния листа каждые N версий. Восстановление на
момент = ближайший снимок плюс проигрывание журнала поверх него.

**`monthly_summaries`** — сводки по месяцам, пересобираются конвейером агрегации.

**`processed_messages`** — идентификаторы обработанных сообщений с TTL-индексом,
защита от повторной обработки при переотправке из очереди.

## Движок формул

Отдельная библиотека `packages/formula-engine` — чистый PHP без Laravel,
подключается в сервис как локальный пакет Composer. Не знает ни про базу, ни про
HTTP: получает значения ячеек через интерфейс-резолвер.

Состав: лексер, парсер с приоритетами операций, узлы синтаксического дерева,
вычислитель, извлечение зависимостей из дерева, планировщик пересчёта с
топологической сортировкой и обнаружением циклов.

Имена функций принимаются в обоих языках и любом регистре: `СУММ`, `SUM`, `сумм`.
В первой версии реализована только сумма.

Ошибки в ячейках: `#ДЕЛ/0!`, `#ЦИКЛ!`, `#ССЫЛКА!`, `#ЗНАЧ!`, `#ИМЯ?`.

**Деньги считаются точной десятичной арифметикой** (`brick/math`), не числами с
плавающей точкой. Классическая ошибка `0.1 + 0.2 = 0.30000000000000004` в приложении
про деньги недопустима.

Эта библиотека пишется через разработку от тестов: у каждого правила есть чёткий
ответ на входе и выходе, а правил десятки, и без тестов они ломают друг друга.

## Слои внутри сервисов

Повторяется раскладка из `old-joe`: домены живут отдельно от каталога Laravel.

```
src/
  app/                    каркас Laravel
  Finance/Domains/<Домен>/
      Controllers/        разбор запроса и формирование ответа
      Actions/            один сценарий — один класс
      Requests/           валидация входа
      Repositories/       единственное место, знающее про MongoDB
      Contracts/          интерфейсы
      Drivers/            обращения к соседнему сервису
      Resources/          сериализация ответа
      Enums/
      Exceptions/
      Providers/
      Subscribers/
```

Домены `sheet-service`: `Auth`, `Workbooks`, `Sheets`, `Cells`, `Calculation`,
`Realtime`, `Core`.

Домены `history-service`: `Changelog`, `Snapshots`, `Summaries`, `Messaging`, `Core`.

Правило: контроллер не знает про базу, действие не знает про HTTP, репозиторий
не содержит бизнес-логики. Проверяется архитектурными тестами.

## Фронтенд

Vue 3, TypeScript, Vite, Pinia, vue-router, Tailwind. Nuxt сознательно не берём:
без серверной отрисовки от него остаются автоимпорты, ради которых тащить
фреймворк смысла нет, а таблица за логином в серверной отрисовке не нуждается.

Раскладка по слоям:

```
src/
  app/        точка входа, роутер, провайдеры
  shared/     ui-кит, клиент API, утилиты
  entities/   типы и преобразования домена
  features/   sheet-grid, formula-bar, cell-format, sheet-tabs, history-panel, auth
  pages/
  stores/
```

Сетка отрисовывает только видимые строки, заголовки колонок и строк закреплены.
Телефон — основной сценарий работы, поэтому у мобильной версии отдельная раскладка:
крупные ячейки, панель ввода снизу над клавиатурой, числовая клавиатура для
числовых ячеек, горизонтальный скролл с прилипшей первой колонкой.

## Аутентификация

Почта и пароль. `sheet-service` выдаёт короткоживущий токен доступа, подписанный
закрытым ключом, и долгоживущий токен обновления, лежащий в базе с TTL-индексом.

`history-service` проверяет токен доступа открытым ключом самостоятельно, не обращаясь
к соседнему сервису. Ключи выдаются через переменные окружения.

## Тестирование

**Движок формул** — разработка от тестов, покрытие полное.

**Сервисы** — Pest: модульные тесты действий, функциональные тесты HTTP-слоя против
настоящей MongoDB в контейнере, архитектурные тесты границ между слоями.

**Фронтенд** — Vitest для сторов и чистых функций.

**Сквозные** — Playwright: вход, ввод формулы и пересчёт итогов, создание месяца
копией, синхронизация между двумя браузерами, поведение при обрыве связи,
мобильный размер экрана.

**Сборка** — GitHub Actions: статический анализ PHPStan на максимальном уровне,
проверка стиля, все наборы тестов, сборка образов.

Отдельно оговаривается: удобство работы пальцем на настоящем телефоне
автоматикой не проверяется, это остаётся за владельцем.

## Развёртывание

Бесплатная виртуальная машина Oracle Cloud Always Free, архитектура ARM64 —
все образы выбираются с её учётом.

Сборка образов в GitHub Actions, публикация в реестр GitHub, на машине —
получение образов и перезапуск. Домен и сертификат — бесплатные.

Один репозиторий на GitHub: два сервиса, фронтенд, библиотека формул,
файлы контейнеров, сборка и документация в одном месте.

## Принятые допущения

Решения, принятые самостоятельно; каждое можно пересмотреть.

1. Имена функций работают и по-русски, и по-английски.
2. Лист по умолчанию 200 строк и 26 колонок (`A`–`Z`), расширяется по запросу.
3. Выгрузка листа в CSV делается попутно — она почти бесплатна. Полноценный
   импорт xlsx не делается.
4. Снимок листа для истории берётся каждые 100 версий.
5. Токен доступа живёт 15 минут, токен обновления — 60 дней, чтобы на телефоне
   не приходилось входить заново.
6. Домен для публичного развёртывания — бесплатный поддомен; выбор конкретного
   откладывается до шага развёртывания.
