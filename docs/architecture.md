# Карта проекта

Кто из чего состоит, кто с кем разговаривает и почему именно так.

## Общая картина

```
          браузер (Vue 3)
             │   ▲
     запросы │   │ правки второго устройства
             ▼   │
   traefik ──┬── сервис таблиц ──── MongoDB (finance_sheets)
             │        │      ▲
             │        │      └── движок формул (библиотека, не сервис)
             │        │
             │        ├── вещание (Reverb) ──► браузеры, подписанные на лист
             │        │
             │        └── очередь (RabbitMQ) ──► сервис истории ── MongoDB (finance_history)
             │                                        ▲
             └── запросы истории ─────────────────────┘
```

Всё живёт в контейнерах на портах 8088 и 8448, разбор по именам делает traefik:
`finance.localhost` — фронтенд, `api.` — сервис таблиц, `history.` — сервис
истории, `ws.` — вещание, `rabbit.` и `mail.` — панели брокера и почты.

## Кто за что отвечает

**Движок формул** (`packages/formula-engine`) — библиотека без единого запроса
в базу. Лексер, разбор в дерево, вычисление на точной десятичной арифметике,
извлечение зависимостей, планировщик пересчёта и переписывание ссылок при
перестройке листа. Ни про MongoDB, ни про HTTP он не знает: это позволяет
проверять его быстрыми тестами без окружения вообще.

**Сервис таблиц** (`services/sheet-service`) — всё, что человек делает руками:
вход, книги, листы, ячейки, оформление, пересчёт, вставка и удаление строк,
выгрузка в CSV. Здесь же живёт единственная копия правды о содержимом.

**Сервис истории** (`services/history-service`) — журнал изменений, снимки
и сводки. Он отдельный не ради моды: журнал растёт быстрее самих данных,
читается редко и никогда не должен задерживать правку.

**Фронтенд** (`frontend`) — Vue 3 с разделением на `shared / entities /
features / pages / stores`.

## Путь правки

1. Браузер шлёт пачку правок в сервис таблиц.
2. Сервис разбирает формулы **до** записи: одна сломанная отменяет всю пачку,
   и прежнее содержимое остаётся нетронутым.
3. В транзакции пишутся ячейки, строится план пересчёта по зависимостям
   и пересчитывается всё задетое. Версия листа растёт одним атомарным шагом.
4. Изменённые ячейки уходят в закрытый канал `sheet.{id}` — второе устройство
   видит их сразу, без перезагрузки.
5. Те же ячейки публикуются в обменник `finance.events`. Сервис истории
   забирает их из очереди и пишет журнал.

Порядок важен: и вещание, и публикация идут после завершённой транзакции.
Сбой любого из них не роняет правку — данные уже записаны, а клиент догонит
состояние по разрыву версий.

## Что держит систему при сбоях

**Разрыв версий.** Пакет применяется, только если его версия ровно следующая.
Разрыв означает, что между ними было что-то не доехавшее, и лист перечитывается
целиком, а не достраивается по кускам.

**Недоступная очередь** не ломает правку: неотправленное складывается
в `pending_messages` и досылается командой `finance:resend-pending-messages`.

**Повторная доставка** обезврежена уникальным индексом по идентификатору
сообщения; отметки живут неделю и убираются по сроку жизни.

**Сервис истории не ходит к соседу за проверкой входа**: он проверяет токен
открытым ключом сам. Иначе недоступность сервиса таблиц гасила бы и историю.

## Почему MongoDB и почему набор реплик

Подробный разбор — в [mongodb.md](./mongodb.md). Коротко: ячейки лежат отдельной
коллекцией, а не массивом внутри листа, иначе правка одной ячейки переписывала бы
весь лист и двое правящих затирали бы друг друга. Набор реплик из одного узла
нужен не ради запаса прочности, а потому что без него нет ни транзакций,
ни потоков изменений.

## Границы слоёв

Контроллер не знает про базу, действие не знает про HTTP, репозиторий не содержит
бизнес-логики. Внутри сервиса код разложен по доменам (`Auth`, `Workbooks`,
`Sheets`, `Cells`, `Calculation`, `Realtime`, `Messaging`, `History`), а не по
типам классов: домен целиком видно в одной папке.
