# MongoDB в этом проекте

Разбор решений по базе на живом коде. Не справочник по синтаксису — объяснение,
почему в каждом месте сделано именно так и что было бы, если сделать иначе.

## Что такое MongoDB на самом деле

Расхожее «монга хранит ключ-значение» — неверно. Ключ-значение это Redis:
положил по ключу, забрал по ключу, больше ничего.

MongoDB — **документная база**. Единица хранения — документ, похожий на JSON,
с вложенностью и массивами. Документы лежат в коллекциях, коллекции в базе.
Аналогия с реляционной базой прямая:

| Реляционная база | MongoDB |
|---|---|
| таблица | коллекция |
| строка | документ |
| колонка | поле документа |
| `JOIN` | `$lookup` (есть, но применяется редко) |

Отличий от таблицы два, и оба важны.

**Схемы нет.** Два документа в одной коллекции могут иметь разный набор полей.
База не проверит, что у ячейки есть поле `kind`, — это забота приложения.
Свобода приятная, но обратная сторона в том, что опечатка в имени поля не вызовет
ошибку: запрос просто ничего не найдёт.

**Вложенность настоящая.** Поле может быть массивом или другим документом, и по
содержимому этого массива строятся индексы и запросы. В реляционной базе такое
потребовало бы отдельной таблицы и соединения.

Запросы полноценные: фильтры, сортировки, агрегации, транзакции. По выразительности
это ближе к SQL, чем к Redis.

## Решение 1. Почему ячейки — отдельная коллекция

Это главное решение в проекте, и напрашивается противоположное.

Раз документ может содержать вложенные структуры, кажется естественным хранить
лист одним документом с массивом ячеек внутри:

```json
{
  "_id": "...",
  "name": "10.26",
  "cells": [
    { "row": 3, "column": 2, "input": "120" },
    { "row": 4, "column": 2, "input": "80" }
  ]
}
```

Лист читается одним запросом, всё рядом, красиво. Так делать нельзя, и причин три.

**Конкурентная запись.** В MongoDB атомарна операция над **документом**. Правка
одной ячейки — это запись всего документа листа. Вы правите `B5`, жена одновременно
`D7`; кто записал вторым, тот и перезаписал лист целиком — вместе с чужой правкой.
Ровно та беда, ради избавления от которой затевался проект.

**Потолок в 16 мегабайт.** Документ не может быть больше. Лист с оформлением на
несколько тысяч ячеек к этому потолку подбирается, и упереться в него означает,
что таблица однажды перестанет сохраняться.

**Поиск зависимых ячеек.** При правке `B5` нужно найти все формулы, которые на неё
ссылаются. При отдельной коллекции это запрос по индексу. При вложенном массиве —
вычитать весь лист и перебрать его в памяти на каждую правку.

Поэтому ячейка — отдельный документ (`Finance/Domains/Cells/Models/CellModel.php`):

```json
{
  "sheet_id": "...",
  "row": 3,
  "column": 2,
  "input": "=СУММ(B3:B90)",
  "kind": "formula",
  "value_number": Decimal128("250"),
  "depends_on_ranges": [{ "min_row": 3, "max_row": 90, "min_column": 2, "max_column": 2 }]
}
```

Теперь правки разных ячеек не пересекаются вовсе: это разные документы.

**Общее правило,** которое стоит унести с собой: вкладывать данные внутрь документа
имеет смысл, когда они читаются и пишутся **только вместе с родителем** и их
количество ограничено. Оформление ячейки — внутрь, оно без ячейки бессмысленно.
Ячейки листа — наружу, они правятся поодиночке и их тысячи.

## Решение 2. Индексы и как проверить, что они работают

Индексы объявлены рядом с репозиториями, которые ими пользуются
(`CellRepository::indexes()`), и создаются командой `php artisan finance:create-indexes`.
Миграций схемы в MongoDB нет, потому что нет схемы; индексы — единственное,
что требует подготовки.

### Составной уникальный

```php
new IndexDefinition(
    name: 'cells_sheet_position_unique',
    keys: ['sheet_id' => 1, 'row' => 1, 'column' => 1],
    unique: true,
)
```

Две ячейки в одной позиции одного листа невозможны. Проверять это кодом
недостаточно: между «проверил, что нет» и «вставил» всегда есть зазор, в который
проскакивает второй запрос. Уникальность гарантирует только база.

**Порядок полей в составном индексе имеет значение.** Индекс
`{sheet_id, row, column}` годится для запросов по `sheet_id`, по паре
`sheet_id + row` и по всем трём. Для запроса по одному `column` он бесполезен.
Работает правило приставки: используется только начало индекса, слева направо.

### Многоключевой

```php
new IndexDefinition(name: 'cells_dependencies', keys: ['sheet_id' => 1, 'depends_on_cells' => 1])
```

`depends_on_cells` — массив адресов вида `["B3", "F2"]`. Когда индексируемое поле
массив, MongoDB заводит **отдельную запись индекса на каждый элемент**. Такой индекс
называется многоключевым, и заводится он сам, без специального указания.

Благодаря ему запрос «кто ссылается на `B3`» превращается в точное попадание
по индексу. В реляционной базе для этого понадобилась бы таблица связей.

### Убирающий по сроку

```php
new IndexDefinition(name: 'refresh_tokens_expiry', keys: ['expires_at' => 1], expireAfterSeconds: 0)
```

База сама удаляет документ, когда время в поле `expires_at` прошло. Чистить
просроченные токены заданием по расписанию не нужно. Фоновый процесс обходит
коллекцию примерно раз в минуту, поэтому удаление не мгновенное — на просроченные
токены всё равно стоит проверять условие в запросе, что и сделано
в `RefreshTokenRepository::findValidByHash`.

### Как убедиться, что индекс используется

```
make mongo
use finance_sheets
db.cells.find({ sheet_id: "...", depends_on_cells: "B3" }).explain("executionStats")
```

Смотреть на две вещи в выводе:

- `winningPlan.stage` — должно быть `IXSCAN` (просмотр индекса). Если `COLLSCAN` —
  база перебирает всю коллекцию, индекса нет или он не подходит.
- `executionStats.totalDocsExamined` против `nReturned` — сколько документов
  пришлось прочитать ради скольких найденных. Если прочитано втрое больше, чем
  найдено, индекс работает лишь частично.

Это самый полезный навык при работе с MongoDB: не гадать, а спросить у базы.

## Решение 3. Запрос по границам диапазонов

Формула `=СУММ(B3:B90)` зависит от 88 ячеек. Хранить 88 адресов в
`depends_on_cells` можно, но это 88 записей индекса вместо одной пары границ,
и при диапазоне на тысячу строк становится совсем плохо.

Поэтому диапазоны хранятся границами:

```json
"depends_on_ranges": [{ "min_row": 3, "max_row": 90, "min_column": 2, "max_column": 2 }]
```

А поиск зависимых выглядит так (`CellRepository::dependentsOf`):

```php
$filter = [
    'sheet_id' => $sheetIdentifier,
    '$or' => [
        ['depends_on_cells' => $reference->key()],
        ['depends_on_ranges' => ['$elemMatch' => [
            'min_row' => ['$lte' => $reference->row],
            'max_row' => ['$gte' => $reference->row],
            'min_column' => ['$lte' => $reference->column],
            'max_column' => ['$gte' => $reference->column],
        ]]],
    ],
];
```

Ключевой здесь `$elemMatch`. Без него условия проверялись бы **по массиву целиком**:
нашёлся бы документ, у которого один диапазон подходит по строке, а другой —
по колонке, хотя ни один не подходит по обоим сразу. `$elemMatch` требует, чтобы
все условия выполнились **на одном элементе массива**. Это одна из самых частых
ошибок новичков в MongoDB, и ловится она не сразу: запрос работает, но иногда
возвращает лишнее.

Запрос написан языком базы напрямую, а не построителем Eloquent. Это осознанно:
такое условие построителем не выражается, а попытка выразить сделала бы код
менее понятным, чем сам запрос.

## Решение 4. Decimal128 для денег

`Finance/Domains/Core/Casts/Decimal128Cast.php`.

Обычное число в MongoDB — двоичное с плавающей точкой, тот же `double`, что в PHP.
На нём `0.1 + 0.2` не равно `0.3`, и в таблице расходов это однажды вылезает
расхождением в копейку, которое невозможно объяснить жене.

Вариантов хранения три:

| Способ | Точность | Сортировка и суммирование в базе |
|---|---|---|
| `double` | теряется | да |
| строка | сохраняется | нет |
| `Decimal128` | сохраняется | да |

`Decimal128` — отдельный тип BSON, десятичное число с 34 значащими цифрами.
Он и точен, и остаётся числом: по нему работают сортировка, сравнение и
суммирование в конвейере агрегации. Для денег это единственный правильный выбор.

В приложении значение представлено `Brick\Math\BigDecimal`, преобразование в обе
стороны делает приведение типа Eloquent.

## Решение 5. Набор реплик из одного узла

В `docker-compose.yml` MongoDB запускается с `--replSet=rs0`, хотя узел один
и отказоустойчивость тут ни при чём.

Причина в том, что **транзакции и потоки изменений работают только в наборе реплик**.
Одиночный узел их не поддерживает. Технически это связано с тем, что оба механизма
опираются на журнал операций `oplog`, который ведётся только при репликации.

Транзакция нужна в `ApplyCellEditsAction`: пачка правок пишет несколько документов,
и промежуточное состояние наружу попадать не должно.

```php
DB::connection('mongodb')->transaction(
    fn (): AppliedCellEdits => $this->apply(...),
);
```

Важная оговорка: транзакция в MongoDB **дороже**, чем в реляционной базе, и её не
стоит раскидывать всюду. Операция над одним документом атомарна и без транзакции —
обновление ячейки, увеличение версии, вставка записи журнала в ней не нуждаются.

## Решение 6. Атомарное увеличение версии

`SheetRepository::incrementVersion`:

```php
$this->collection()->findOneAndUpdate(
    ['_id' => new ObjectId($identifier)],
    ['$inc' => ['version' => 1]],
    ['returnDocument' => FindOneAndUpdate::RETURN_DOCUMENT_AFTER],
);
```

Напрашивающийся способ — прочитать версию, прибавить единицу, записать обратно —
сломан. Два одновременных запроса прочитают одно и то же значение и запишут одно
и то же новое. Версия пропустит шаг, а на ней держится вся синхронизация между
устройствами: клиент увидит разрыв в номерах там, где его нет, и полезет
перезагружать лист.

`$inc` выполняется **на стороне базы** одной атомарной операцией. Никаких блокировок
в коде не нужно, и это общий приём: любое «прочитать, изменить, записать» лучше
заменять оператором обновления. Их много: `$inc`, `$set`, `$unset`, `$push`,
`$pull`, `$addToSet`, `$min`, `$max`.

`returnDocument: AFTER` возвращает документ уже после изменения — так новая версия
получается той же операцией, без второго запроса.

## Грабли, на которые мы наступили

Обе стоили времени и обе неочевидны.

**Приведение `array` в модели ломает хранение.** Пакет `mongodb/laravel-mongodb`
при приведении `'depends_on_cells' => 'array'` сериализует массив **в строку JSON**.
В базе оказывается текст, а не массив, и запрос по элементу перестаёт что-либо
находить — молча, без ошибки. MongoDB хранит массивы родным типом, и приведение
здесь не нужно вовсе. Пакет предупреждает об этом уведомлением об устаревании,
которое легко пропустить в потоке вывода.

**Поле с собственным приведением типа не обновляется через Eloquent.**
Самая дорогая находка. `$model->fill(['value_number' => '300'])->save()` на
существующей записи отправляет в базу только те поля, которые Eloquent считает
изменившимися, и поле с собственным приведением типа (`Decimal128Cast`) в этот
список не попадает. В памяти новое значение есть, в базе остаётся прежнее.

Коварство в том, что обычным тестом это не ловится: ответ формируется из модели
в памяти и показывает правильное число. Мы нашли ошибку, только когда тест
перечитал лист отдельным запросом — и увидел прежний итог. В работающем
приложении это выглядело бы так: правишь расход, итог пересчитывается на глазах,
а после перезагрузки страницы возвращается старый.

Лечится отказом от Eloquent в этом месте: запись идёт одним запросом
`updateOne` с `upsert`. Заодно это правильнее по сути — «создать или обновить»
и есть одна операция, а не чтение с последующим сохранением.

**Сырой запрос через коллекцию идёт мимо транзакции.**
Прямое следствие предыдущего исправления. Сессию транзакции открывает Laravel,
а запрос через `getCollection()` о ней не знает: запись оказывается вне
транзакции, и чтение внутри неё этой записи не видит. Сессию нужно передавать
явно — в проекте это делает `AbstractMongoRepository::sessionOptions()`.

**Имя метода модели не должно совпадать с именем поля.** Метод `kind()` рядом
с полем `kind` приводил к тому, что Eloquent принимал поле за связь и возвращал
`null` вместо значения. Переименовали в `cellKind()`. То же правило действует
и в классах запросов: `format()` занято классом `Request` самого Laravel.

## Что стоит попробовать руками

```
make mongo
```

```javascript
use finance_sheets

// Посмотреть, как выглядит документ ячейки
db.cells.findOne({ kind: "formula" })

// Какие индексы есть у коллекции
db.cells.getIndexes()

// Проверить, что поиск зависимых идёт по индексу, а не перебором
db.cells.find({ sheet_id: "...", depends_on_cells: "B3" }).explain("executionStats")

// Конвейер агрегации: сумма всех числовых значений по листам
db.cells.aggregate([
  { $match: { value_number: { $ne: null } } },
  { $group: { _id: "$sheet_id", total: { $sum: "$value_number" } } },
  { $sort: { total: -1 } }
])
```

Последний пример — это то, на чём будут построены месячные сводки в сервисе истории.
Конвейер агрегации читается сверху вниз: каждая ступень получает то, что выдала
предыдущая. `$match` отбирает, `$group` схлопывает по ключу, `$sort` упорядочивает.
Ставить `$match` первым важно: он отсекает документы до того, как начнётся тяжёлая
работа, и может опереться на индекс.
